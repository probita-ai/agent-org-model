One Jira ticket, followed through every level of the org

This page traces PLAT-412 “Rate limit the public /export API” from the board’s quarterly goal down to merged code in production. At each level it shows what the seat receives, what it decides and what it passes on. It also covers how the coder works through the ticket, talks to the PM and estimates the work.

1 · The big picture

Agents run in one layer. Everything that limits them is plain software.

Agents never call the outside world directly. Every tool call passes the policy engine and every model call passes the metered gateway. The kill switch revokes keys at those two points, so stopping an agent never depends on the agent cooperating.

Humans Control plane (deterministic) Agents Platform services - - → kill switch path
  • Authority flows down onlyA seat can grant at most what it holds. No seat raises its own capacity, autonomy or permissions.
  • Every change has a before-stateRollback is a ledger operation, not a request to an agent.
  • Humans are a budgeted resourceHuman minutes are reserved and metered like dollars, because they’re usually what runs out first.

3 · Every level, in detail

Each seat uses the same card: in, decides, out, escalates, scored on

Sprints run out of human minutes before dollars. In planning, the lead fills the sprint until the P90 cost reaches the crew’s capacity minus a 15% reserve ($980 of $1,020). It then drops PLAT-421 because PM minutes came to 410 against Dana’s 300 per week. The lead has to fit both budgets.
4 · Inside the coder seat

Twelve phases, each a resumable step with its own trace and cost

The coder never starts writing code from the raw ticket. It first maps every acceptance criterion to a test; any criterion it can’t test is marked ambiguous and goes to the PM. This one rule catches most unclear tickets. For medium-risk work the reviewer approves the plan before any code is written, which costs about $0.40 and avoids $15 spent on the wrong approach.

5 · Discussing with the PM

One batch of questions, each with options and a default

The coder asks everything in one message, tags each question as blocking or not, and says how many PM minutes it expects the questions to take. A PM-assist agent first answers what it can from the docs. In this case Dana picks an answer the coder didn’t expect (limit per org, not per API key), which is why asking beats assuming. The coder can suggest new acceptance-criteria wording, but only the PM can accept it.

6 · Estimation

Points for people, P50/P90 for the budget, minutes for the humans

An agent estimate has four parts: story points, so humans and agents share one scale; agent cost as P50 and P90, which sets the budget reservation; wall-clock time; and human minutes, which are often the real limit. The method starts from similar past jobs, applies written-down adjustments, then has three seats estimate blind.

7 · Context and memory

Each handoff adds context. Nothing is just forwarded.

Long chains of agents lose context at every handoff. Briefs are the fix: each has fixed fields, links to sources instead of pasting summaries, and every level adds what only it knows. Anything recorded as a decision is added to the context of every later step on that ticket.

8 · Capacity enforcement

Shares flow down by percentage; each job reserves its P90

The monthly share caps a seat’s total spend, and each job also reserves its own budget. At 80% of the reservation the agent pauses at the next step boundary and must re-estimate. At 100% the gateway refuses further model calls. The lead can top a job up from the crew reserve, but only within its own authority.

9 · Risk gates and permits

Every tool call is classified, not every agent

The policy engine checks the action’s risk against the seat’s autonomy level and risk ceiling. The result is one of three: allow, approve first, or refuse. Every decision is written to the ledger.
